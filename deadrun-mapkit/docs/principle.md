# 지도를 내려받아 저장하고 실행하는 원리

## 전체 흐름

```
[굽기 — 내 PC에서 1회]
  OSM(Overpass) → 필요한 태그만 추출 → ENU 미터로 변환
                → 0.25m 정수로 양자화 → 차분 인코딩 → .drmp 타일
                → 정적 호스팅에 업로드

[실행 — 앱에서 매번]
  내 GPS → 타일 번호 계산 → 저장소에 있나?
                              ├ 있음 → 그대로 사용 (네트워크 안 씀)
                              └ 없음 → HTTPS GET → 저장 → 사용
         → 여러 타일을 "지금 내 위치" 기준으로 재투영해 합침
         → RoadGraph.build() → 기존 게임 로직 그대로
```

---

## 1. 왜 타일로 자르나

지도 전체를 한 파일로 두면 전국 270MB를 통째로 받아야 한다. 격자로 잘라두면
**내 주변 것만** 받으면 된다.

격자는 슬리피맵(XYZ) 표준을 쓴다. 줌 `z`에서 세상은 `2^z × 2^z` 칸이고,
위경도를 넣으면 **계산으로** 타일 번호가 나온다. 색인을 뒤질 필요가 없다.

```ts
x = floor((lon + 180) / 360 × 2^z)
y = floor((1 − ln(tan φ + sec φ) / π) / 2 × 2^z)
```

이 프로젝트는 **z13**을 쓴다. 서울 위도에서 한 변 3.88km다.

| 줌 | 타일 크기 | 전국 타일 수 | 판단 |
|---|---|---|---|
| z12 | 7.8km | 4,320 | 불필요한 데이터를 많이 받음 |
| **z13** | **3.9km** | **17,172** | **기본** — 반경 1km 플레이에 보통 1~4장 |
| z14 | 1.9km | 68,370 | 세밀하지만 파일 수가 git에 부담 |

실제로는 바다·산속 타일에 데이터가 없어 파일이 생기지 않는다. 국토 기준 실제 파일은
약 5,000개 수준이다.

---

## 2. 왜 JSON이 아니라 바이너리인가

Overpass가 주는 JSON은 **반경 1km 도로+건물이 1,256KB**다. 같은 내용이 `.drmp`로는
**55KB**다. 23배 차이가 어디서 나오는지가 포맷의 핵심이다.

### ① 필요 없는 것을 버린다

OSM way 하나에는 편집 이력·기여자·수십 개 태그가 딸려온다. 게임에 필요한 건
`highway` 종류, `bridge`/`tunnel`, 좌표뿐이다.

### ② 좌표를 정수로 줄인다

좌표 하나를 `double` 두 개로 두면 16바이트다. 대신

- 타일 중심 기준 **ENU 미터**로 바꾸고
- **0.25m 단위 정수**로 양자화하고
- 각 도로의 **첫 점만 `int32`**, 이후 점은 **직전 점과의 차이를 `int16`**

으로 담으면 **점당 4바이트**가 된다. 도로의 인접한 두 점은 보통 수십 m 이내라
`int16`(±8.1km) 안에 충분히 들어간다.

양자화 오차는 최대 12.5cm다. 도로 그래프가 어차피 **0.5m 격자로 노드를 병합**하므로
게임 판정에는 영향이 없다. (검증: 왕복 오차 16.3cm, 병합 격자보다 작음)

### 레이아웃

```
헤더 40B
   0  magic 'DRMP'   u32
   4  version        u8
   6  quantMm        u16   좌표 1단위의 mm (250 = 0.25m)
   8  originLat      f64   이 타일의 기준점
  16  originLon      f64
  24  roadCount      u32
  28  buildingCount  u32
  32  z u8, x u16, y u16   어느 타일인지 스스로 기록
레코드 (도로 → 건물)
  u8  kind    도로 종류 인덱스 / 건물은 255
  i8  layer   -1 지하 · 0 지상 · 1 고가
  u16 pointCount
  i32 x0, y0
  (n-1) × (i16 dx, i16 dy)
```

`kind`는 인덱스로 저장하므로 **`HIGHWAY_KINDS` 배열의 순서를 바꾸면 기존 팩을 못 읽는다.**
종류를 추가할 때는 반드시 **끝에** 붙일 것.

---

## 3. 좌표계가 타일마다 다른 문제

각 타일은 **자기 중심**을 기준점으로 좌표를 저장한다. 그래야 숫자가 작아져 차분
인코딩이 짧아진다. 그런데 게임은 **현재 GPS 위치**를 원점으로 쓴다. 기준점이 서로 다르다.

그래서 읽을 때 재투영한다.

```
타일 ENU → (타일 기준점으로) 위경도 → (플레이 원점으로) ENU
```

여러 타일을 합칠 때 **반드시 같은 `playOrigin`을 넘겨야** 좌표계가 하나로 맞춰진다.
이게 어긋나면 타일 경계에서 도로가 어긋나 붙는다.

(검증: 1km 떨어진 원점으로 재투영 시 오차 3.3cm)

---

## 4. 타일 경계에서 길이 끊기는 문제

도로는 타일 경계에서 잘린다. 그대로 두면 경계 지점에서 길찾기가 막힌다.

굽을 때 **타일 범위보다 조금 넓게(기본 60m) 받아** 가장자리를 겹치게 한다.
겹친 도로는 이웃 타일에도 들어가지만, 읽는 쪽에서 도로 그래프가 0.5m 격자로 노드를
병합하므로 **자동으로 이어진다**. 중복 엣지가 약간 생기는 건 감수한다.

## 5. 저장과 캐시

```
앱 문서 디렉터리/
  maps/
    latest.json              ← 매니페스트 사본 (오프라인 대비)
    v1/13/6982/3172.drmp     ← 버전 폴더째로 저장
```

**버전 폴더를 그대로 경로에 쓰는 것이 핵심이다.** 새 버전을 올려도 옛 파일과 경로가
달라서 섞이지 않는다. 같은 경로를 덮어쓰면 반쯤 옛 데이터를 읽는 사고가 난다.

### 매니페스트가 하는 일

`latest.json`에는 **실제로 존재하는 타일 목록과 각각의 크기**가 들어 있다.

- 바다·산속처럼 데이터가 없는 타일은 목록에 없으므로 **요청조차 하지 않는다**
- 받은 파일 크기를 목록과 대조해 **중간에 끊긴 다운로드를 검출**한다

### 깨진 데이터 방어

다운로드가 끊기면 조용히 반쪽짜리 지도로 플레이하게 된다. 세 겹으로 막는다.

1. 매니페스트의 크기와 대조
2. 디코더가 **레코드 수를 대조** — 부족하면 예외
3. 실패하면 **캐시 파일을 삭제**해 다음 실행에 다시 받도록

## 6. 실행 시 동작

```ts
const { ways, buildings } = await client.loadAround(currentGps, 1000);
const graph = RoadGraph.build(ways);
```

1. 매니페스트 확인 (없으면 캐시본)
2. 현재 위치 반경을 덮는 타일 번호 계산
3. 타일마다: 캐시 확인 → 없으면 다운로드 → 디코드(재투영)
4. 모든 타일의 도로·건물을 하나로 합침

**두 번째 실행부터는 네트워크를 쓰지 않는다.** 지하철이나 산속에서도 진짜 지도로 플레이된다.

---

## 7. 데이터가 낡는 문제

구운 팩은 **스냅샷**이다. 현실의 도로가 바뀌어도 반영되지 않는다.

다만 도로망 토폴로지는 느리게 변한다. 새 아파트 단지나 도로 개편은 분기 단위 사건이라
**월 1회 리빌드면 실사용에 충분하다**.

더 최신이 필요하면 **하이브리드**로 간다 — 타일을 바탕으로 쓰고, 현재 위치 반경 300m만
Overpass로 조회해 덧입힌다. 실패해도 타일이 있으니 게임은 정상 진행된다.
